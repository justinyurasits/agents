What's an agent

An agent is a language model in a loop. Each turn it decides the next step, usually a request to use a tool. Code carries the step out and hands back the result, and it repeats until the model says the job is done.

  1. The model decides the next step
  2. Code runs the tool it asked for
  3. The result goes back to the model
  4. Repeat until the model says it's done

Claude decides; Python executes. In this agent the model is Claude and the code is Python. Claude never runs anything itself: it can only ask, and Python decides whether and how to carry the request out.

How this agent works

It reads a job posting and rates it for one candidate. Four parts take part in every run:

Python
The agent loop. It calls Claude, runs the tools Claude asks for, and keeps the conversation.
Claude
The model in the main conversation. It reads the posting and every result so far, then asks for a tool or writes its final answer.
The tools
Python functions that do the work. Claude picks them by name; Python runs them.
The grader
A second, separate call to Claude, made from inside evaluate_job. It answers one yes/no question about the work, has no tools, and never sees the main conversation.

The loop. Each pass, Python sends the whole conversation to Claude. If Claude asks for tools, Python runs them, adds the results to the conversation, and sends it again. When Claude answers without asking for a tool, the run ends. The conversation is the agent's only memory.

    Design principles

    Seven principles this agent is built on, the part of the agent that applies each one, and a run where you can watch it. Every guard is listed under the principle it serves: watch the ones a scenario shows; the rest are proven by a test.

    PrincipleIn this agentWatch it
    The model for judgment, code for rules Your hard rules (remote, and a minimum base salary, MIN_BASE) are checked in code, in hard_screens, before the grader is asked. The grader answers one yes/no question, and code turns its answer into a rating with RATING_FOR_ANSWER (D28).
    Tool choice is intent classification, so state precedence Each tool's description says when to use it, and Claude matches the posting against them. research_company and flag_for_review both cover a posting with no pay listed, and neither description says which comes first. Claude researches first on its own (#65).
    Errors go back to the model as information When a tool fails, Python sends the error back to Claude as a tool result marked is_error, instead of crashing, and Claude decides what to do next (D18).
    • Tested, not demonstrated: tests/test_max_tokens.py · test_cut_off_grader_reply_is_reported_as_cut_off_not_invalid_json
    • Tested, not demonstrated: tests/test_grade_validation.py · ThroughTheAgentTest
    Fail closed on the unknown A request for a tool that doesn't exist gets an error listing the real tools (D19). A reply that's cut off, or that stops for a reason the agent doesn't handle, ends the run instead of being acted on (D22, D29).
    • Tested, not demonstrated: tests/test_unexpected_stop.py · StopsTest
    • Tested, not demonstrated: tests/test_api_errors.py · OuterApiErrorTest
    • Tested, not demonstrated: tests/test_final_text.py · NoTextBlockTest
    Bound the loop The loop ends after MAX_PASSES calls to Claude, whatever happens. Scenario 8 lowers the cap to 2 so you can see it (D27).
    Smaller questions get more reliable answers The grader gets one yes/no question about the work, not a list of criteria to weigh: pay and location are already checked in code (D28).
    The conversation is the memory messages holds everything Claude knows about the run. Python sends it whole on every call and adds Claude's request and each result to it.
